# AI-Native Calibration Convergence Implementation Plan

Version: v1.8
Date: 2026-07-27
Status: accepted for staged implementation

## Goal

Converge `calibration` from a growing body of engineering guidance into:

1. a small cross-project judgment kernel;
2. references loaded only for the decision at hand; and
3. executable repository feedback that carries more correctness responsibility
   than prompt text or prescribed implementation process.

The central hypothesis is:

> A narrower calibration surface is an improvement only when it preserves
> correctness and reduces implementation friction on representative writable
> repository tasks.

This plan therefore has one fixed closeout phase, one mandatory evaluation
phase, and three evidence-gated convergence phases. Phases 3 and 4 may close
with `NO-CHANGE`.

## Non-Goals

- Do not add a new skill or document type.
- Do not add `README.html`.
- Do not broaden autonomous permissions.
- Do not remove compatibility, security, permission, verification, or
  human-authority boundaries.
- Do not make multi-agent execution or orchestration a default.
- Do not change the installed AO service, its version, permissions, enrolled
  repositories, or auto-merge state.
- Do not add RAG, durable memory, post-training, or parameter-update systems.
- Do not import chapter structure, named frameworks, current model versions, or
  other source-specific implementation details into cross-project guidance.
- Do not promote one evaluation observation directly into a general rule.

## Assumptions

- `main` at `a4a9a711fbfc50ee093242091af85074341480e9` is the accepted
  pre-candidate baseline.
- The 2026-07-27 read-only comparison is complete and supports regression
  acceptance only.
- The current candidate is retained because its policy direction was accepted
  and it introduced no measured critical or required-behavior regression, not
  because comparative superiority was established.
- Writable evaluation must run in fresh isolated workspaces and must not mutate
  the user's active Codex installation.
- Plans are working hypotheses. Repository evidence may change a phase's
  implementation path without changing its declared outcome, boundary, or
  acceptance gate.

## Phase 2: Build Writable AI-Native Implementation Evaluation

### Outcome

Determine whether the Phase 1 candidate improves real implementation behavior,
not merely read-only answers about intended behavior.

### Evaluation Object

Compare the complete operating combination:

```text
model
+ loaded context
+ tools and permissions
+ writable repository environment
+ executable feedback
```

### Minimum Case Families

#### W01: Direct Local Repair

- A small reversible defect has a discoverable local rule and test entrypoint.
- The task does not change a public contract.
- Success requires editing and verification without a durable specification or
  implementation plan.

#### W02: Evidence Overrides A Plan

- The fixture provides a plausible but incorrect initial diagnosis or plan.
- A stack trace, reproduction, or failing test identifies the real boundary.
- Success requires changing the implementation path rather than mechanically
  completing the initial plan.

#### W03: Failure, Repair, And Reverification

- The initial test is red.
- The first attempted repair or its validation exposes another actionable
  signal.
- Success requires autonomous correction and a final focused plus smoke
  verification loop.

### Evidence Dimensions

Primary gates:

- final tests, artifacts, and repository state;
- required behavior and critical failure;
- local-instruction, compatibility, permission, and public-boundary adherence;
- absence of false completion claims; and
- successful self-correction from executable feedback.

Diagnostic dimensions:

- observation completeness;
- action and tool adequacy;
- feedback quality;
- unnecessary user confirmation;
- abandoned plan or document artifacts;
- rules loaded before the first effective edit; and
- trajectory evidence supporting the failure attribution.

Secondary measures, considered only after primary gates pass:

- turns;
- wall time;
- input and output tokens; and
- tool-call count.

### Frozen Protocol

- Baseline arm: `a4a9a711fbfc50ee093242091af85074341480e9`.
- Candidate arm: the Phase 1 candidate commit.
- Use the same model, reasoning effort, tools, fixture, task prompt, and step
  budget for both arms.
- Start each run in a fresh context and a fresh isolated writable workspace.
- Run one smoke repetition for every arm and case first.
- Continue to three repetitions only after both arms pass every smoke critical
  gate.
- Hide arm identity during pairwise judgment.
- Preserve replayable trajectories and hashes outside the public repository;
  commit only sanitized fixtures, protocol, reviewed findings, schemas, and
  reconstructable references.
- Use a model-swap or component ablation only if a repeated failure cannot be
  attributed to model capability, context, tools, environment, or feedback
  from the primary comparison.

### Decision Gates

Regression acceptance requires:

- no candidate-only critical failure;
- candidate required-behavior coverage not below baseline;
- no unauthorized public-contract change; and
- at least one complete candidate loop in every case family.

Comparative improvement requires all regression gates plus:

- more blind pairwise preferences for the candidate than the baseline; and
- at least two case families showing a repeatable reduction in one
  predeclared implementation-friction measure.

Shorter prose, lower token use, or omitted verification cannot independently
establish improvement.

### Produced Gate

A reviewed finding for each observed difference and a closeout that selects one
of:

- comparative improvement;
- regression acceptance only;
- candidate regression; or
- inconclusive evidence requiring a narrower diagnostic experiment.

## Phase 3: Converge Update Placement And Planning

### Start Gate

Start only if Phase 2 repeatedly shows at least one of:

- ordinary local work creates an unnecessary durable plan;
- a plan suppresses correction from runtime evidence;
- an outcome-only task omits a material durable boundary; or
- an observation is placed in prompt text or cross-project guidance when a
  lower, enforceable owner exists.

Otherwise record `NO-CHANGE`.

### Outcome

Choose the update carrier before changing the plan contract:

```text
current task or trace
-> project document or project skill
-> test, code, schema, or repository harness
-> cross-project calibration judgment
-> model-capability boundary outside calibration
```

Evaluate two planning shapes:

- an ephemeral outcome brief containing goal, boundaries, executable
  acceptance, and non-goals while leaving the implementation path open; and
- the existing decision-complete plan for cross-team, cross-PR, high-risk,
  interruption-sensitive, or explicit handoff work.

Do not create an `outcome-brief.md` document type. Persist an outcome brief only
when coordination, risk, interruption, or repository workflow requires it.

### Conditional Modification Scope

Only when supported by the Phase 2 finding:

- `references/engineering/discipline/harness.md`
- `references/engineering/docs/document-types/implementation-plan.md`
- `references/engineering/docs/document-types/README.md`
- `references/engineering/docs_index.md`
- `skills/calibration/test-prompts.json`
- corresponding tests and evaluation cases
- a dated decision or closeout

### Acceptance Gate

- Reversible local work no longer gains a durable plan by default.
- High-risk and cross-boundary work retains compatibility, dependency,
  rollback, and handoff completeness.
- Mechanically decidable constraints route to code or executable checks rather
  than more prompt text.
- Targeted and regression evaluation pass.

## Phase 4: Separate Core Judgment From Environment Adaptation

### Start Gate

Start only after repeated evidence that:

- ordinary engineering judgment loads irrelevant current-host AO detail;
- AO routing creates an incorrect action, unnecessary confirmation, or material
  context burden;
- core guidance and host operation have conflicting owners or update cadence;
  or
- the current orchestration gate fails on a representative real task.

The single orchestration preference loss in the 2026-07-27 read-only comparison
is an observation, not a sufficient start gate.

Otherwise record `NO-CHANGE`.

### Outcome

Keep the calibration core responsible for:

- cross-project engineering judgment;
- capability placement;
- verification and evaluation;
- general orchestration adoption boundaries.

Keep the environment adapter responsible for:

- current-host AO installation;
- versions and local patches;
- service, permission, identity, recovery, and repository-adoption operation.

Use an information-increment gate for multi-agent or orchestrated execution. It
must add at least one of:

- information unavailable to the generating agent;
- state continuity across interruption;
- genuinely independent parallel work; or
- an existing PR, CI, review, or asynchronous event control plane.

Multiple agents rereading the same text is not an adoption reason.

### Conditional Modification Scope

Only when supported by repeated evidence:

- `references/engineering/discipline/harness.md`
- `skills/calibration/SKILL.md`
- `docs/runbooks/agent-orchestrator-review-continuation.md`
- `codex/AGENTS.md.template`
- `skills/calibration/test-prompts.json`
- corresponding assertions and targeted evaluation
- a dated decision or closeout

Do not modify AO binaries, services, permissions, enrolled repositories, or
auto-merge state.

### Acceptance Gate

- Ordinary repository judgment does not load host operations.
- Explicit AO adoption, repair, and recovery still route to the runbook.
- The accepted AO delivery contract does not regress.
- Tasks without an orchestration need remain single-agent.
- Tasks with demonstrated state-continuity or event-loop needs are not
  incorrectly rejected.

## Phase 5: Retire Harness Layers And Converge Documentation

### Start Gate

Start after Phases 2 through 4 have stable decisions. Do not delete rules that
are still under evaluation.

### Outcome

Make current authority easy to load and delete only harness layers whose
responsibility has moved to a model, tool, test, repository, or platform
capability.

Restructure `docs/README.md` around:

```text
Current Authority
Current Operational Surface
Open Evidence Gaps
Historical Decisions
```

Keep historical files in place unless a broken fact or link requires repair.
Do not add an HTML mirror.

### Retirement Test

For every candidate rule, record:

- the repeated failure it addressed;
- the capability that now owns the behavior;
- deletion or ablation evidence;
- whether it still protects a public, compatibility, safety, permission, or
  human-authority boundary; and
- its retained scope or retirement result.

Delete only when representative evaluation or real-task evidence shows no
required-behavior regression.

### Modification Scope

Required:

- `docs/README.md`

Evidence-dependent:

- `references/engineering/principles.md`
- `references/engineering/discipline/harness.md`
- `references/engineering/discipline/evaluation.md`
- `skills/calibration/SKILL.md`
- `codex/AGENTS.md.template`
- corresponding prompts, assertions, and regression cases
- a final convergence closeout

### Acceptance Gate

- The default documentation path presents current state rather than chronology.
- Current authority, operational entrypoints, and open evidence gaps are
  directly discoverable.
- Every retained harness layer has an evidence-backed purpose and a retirement
  condition or an explicit durable-boundary reason to remain.
- Deleted guidance passes targeted and regression evaluation.
- Skill names, installer behavior, and public repository contracts remain
  compatible.

## Dependency And Stop Graph

```text
Phase 1 candidate closeout
    -> Phase 2 writable evaluation
        -> Phase 3 finding gate -> change or NO-CHANGE
        -> Phase 4 repeated-evidence gate -> change or NO-CHANGE
        -> Phase 5 evidence-backed retirement and navigation closeout
```

Stop a phase when:

- its start gate is not met;
- evidence contradicts its proposed intervention;
- the candidate loses required behavior or introduces a critical failure; or
- completion requires a product, compatibility, risk, or irreversible decision
  not already authorized.

Stopping with a recorded `NO-CHANGE` is a successful convergence outcome.

## Delivery Structure

Use separate semantic review boundaries for:

1. the current candidate and this plan;
2. writable evaluation infrastructure and fixtures;
3. writable evaluation result and closeout;
4. evidence-supported plan or placement changes, if any;
5. evidence-supported environment-routing changes, if any; and
6. final retirement and documentation convergence.

These review boundaries do not add implementation phases. Conditional phases
may produce only a closeout.

For each pull-request boundary, use the repository's accepted AO task intake
when runtime-ready. If AO is unavailable, use an isolated worktree and report
the fallback. Merge and risk acceptance remain user decisions.

## Final Acceptance

The convergence is complete when:

- calibration's default trigger surface has not expanded;
- representative reversible implementation tasks close autonomously;
- public, compatibility, safety, permission, and human-authority boundaries
  remain protected;
- tests, tools, runtime evidence, and repositories carry more enforceable
  correctness responsibility than prompt text;
- durable plans are triggered by coordination, risk, interruption, handoff, or
  explicit repository workflow rather than code change alone;
- host AO operation does not pollute ordinary engineering judgment;
- current documentation is the default route and history is on demand; and
- every retained harness layer has a documented reason to remain.
