# v1.9 Persistent Linear Intake and No-product Canary Implementation Plan

Date: 2026-07-28

Status: pending live canary

Issue: FUQ-14

## Goal

Opt `calibration` into one persistent, project-scoped Linear Symphony lane and
use one controlled documentation-only issue plus one read-only concurrency
probe to establish whether the deployed AO service can claim, enforce its
concurrency ceiling, recover, retry, reconcile, continue review work, and
observe Linear progress without enabling auto-merge.

The repository contract is durable after this plan and `WORKFLOW.md` merge.
Operational acceptance remains pending until the live canary produces the
evidence below.

## Non-goals

- Do not change skills, behavioral evaluations, AO binaries, the accepted
  service deployment, credentials, or host permission defaults.
- Do not add workflow hooks. The installed AO intake lane does not execute
  repository lifecycle hooks, so declaring them would create a false runtime
  contract.
- Do not enroll another repository or Linear project.
- Do not give the tracker adapter write authority or place a Linear credential
  in the repository or worker configuration.
- Do not change product code during the canary.
- Do not enable auto-merge or authorize AO to merge a pull request.
- Do not describe the lane as accepted, production-proven, or generally
  reusable before the live canary passes.

## Ownership Boundaries

- Root `WORKFLOW.md` owns issue eligibility, the Linear project UUID, normalized
  active and terminal states, the 30-second polling interval, the one-agent
  concurrency ceiling, and the worker prompt.
- `AGENTS.md` and `README.md` own repository setup, validation, delivery, and
  installer safety. The workflow prompt delegates to those authorities instead
  of copying their commands.
- This plan owns rollout order, canary evidence, acceptance, and rollback.
- AO's accepted user service owns persistent polling, durable claims,
  reconciliation, retry scheduling, isolated worktrees, and review
  continuation.
- Linear owns issue labels and state. A human canary operator owns deliberate
  label and state transitions; the AO tracker adapter remains read-only.
- The task worker owns the implementation branch, repository validation,
  commits, push, and pull-request updates.
- GitHub Actions and Automatic Codex Review own remote mechanical and review
  feedback. The user retains merge and risk authority.
- Host configuration and the Linear credential remain outside Git. This pull
  request records commands but does not execute the rollout.

## Slice 3: Controlled No-product Canary

Create two Linear issues in the configured project:

1. a primary documentation-only issue whose only repository change is to append
   canary evidence and a closeout section to this plan; and
2. a `READ-ONLY PROBE` concurrency issue that must never edit, commit, push, or
   open or update a pull request.

Create both in normalized `open`, without `AO Intake`, and assigned exactly to
`fd781537-bd86-4ad1-b059-5460066338e1`. Read back the project UUID, issue UUID
and identifier, exact assignee UUID, state, labels, and complete description
before continuing. A missing or different assignee fails the precondition and
the issue must not be labeled.

Both descriptions must begin with this dispatch-time pause contract, adapted
only for the issue identifier:

```text
CANARY PAUSE BARRIER
Before any repository mutation, print exactly:
AO_CANARY_PAUSED <ISSUE_IDENTIFIER>
Then wait without editing, committing, pushing, or opening a pull request.
Proceed only after the AO operator sends exactly:
RELEASE AO CANARY <ISSUE_IDENTIFIER> <PHASE>
Any other message does not release the barrier.
```

The primary issue must also name the expected validation contract, forbid
product, skill, evaluation, runtime, host-configuration, credential, and
auto-merge changes, and require a ready-for-review pull request that remains
unmerged until human approval. The concurrency probe description must declare
the exact task mode `READ-ONLY PROBE`, say that every phase is read-only, and
require terminal cleanup without a repository or GitHub write. Because
`WORKFLOW.md` includes `issue.description` and makes delivery conditional on
that declared mode, these barriers and prohibitions are present in the initial
dispatch prompt rather than sent after claim.

Use this controlled sequence:

1. With both exact-assignee issues unlabeled, wait at least two complete
   30-second polling intervals and confirm AO creates no claim, session, branch,
   or pull request for either issue.
2. Add `AO Intake` to both issues within one polling interval. Record both
   issue identities and the workflow revision. Exactly one issue may acquire a
   claim and session; the other must remain eligible but unclaimed for at least
   two complete polling intervals while the first worker remains at its
   `AO_CANARY_PAUSED` marker. More than one workflow agent fails the configured
   concurrency ceiling.
3. While the first worker remains paused, restart only the AO user service,
   then read back the same durable issue claim and owning session. Confirm
   restart creates no duplicate session or attempt.
4. Remove `AO Intake` from the actively claimed issue. Within two complete
   polling intervals, verify AO releases that issue, stops or retires its
   session, and does not redispatch it. The other still-labeled issue may then
   claim the single slot and must reach its own observable
   `AO_CANARY_PAUSED` marker. If the released issue was the concurrency probe,
   move it to `cancelled` immediately after release and leave it unlabeled.
5. Ensure the concurrency probe is cancelled regardless of dispatch order. If
   the newly claimed issue is the probe, remove its label, verify bounded
   release and no redispatch, then move it to `cancelled`. If it was already
   cancelled in Step 4, record that terminal readback. If the primary was
   released in Step 4, re-add `AO Intake` to it only after the probe is
   confirmed cancelled; otherwise leave the primary label in place. Confirm
   the primary becomes the sole claimed issue and reaches
   `AO_CANARY_PAUSED`. This deliberate re-add starts the next phase and proves
   label restoration is explicit rather than automatic.
6. Terminate the paused primary worker through AO to exercise abnormal-exit
   retry. Observe the durable run become retry-queued, then claimed as the next
   attempt after its bounded backoff. Confirm the issue identity and workflow
   revision are retained and never overlap with another active attempt. The
   retried worker must again emit `AO_CANARY_PAUSED`; send
   `RELEASE AO CANARY <PRIMARY_IDENTIFIER> IMPLEMENT` through AO only after all
   claim, restart, label-withdrawal, concurrency, and retry evidence is
   recorded.
7. Move the Linear issue deliberately from normalized `open` to
   `in_progress`. Confirm the read-only adapter observes the state and the
   retry worker continues the same task rather than creating another claim.
8. Let the retry worker make only the planned documentation closeout change,
   run the full repository validation contract, commit, push, and open a
   ready-for-review pull request.
9. Move the Linear issue to normalized `review`. Confirm reconciliation keeps
   the owning worker available and does not create a replacement.
10. In the first reviewable closeout revision, deliberately include exactly
    `Canary status: accepted before live evidence.` under the canary evidence
    heading. This bounded documentation defect directly contradicts this
    plan's acceptance boundary. Request Automatic Codex Review and require the
    actionable thread to come from allowed author
    `chatgpt-codex-connector` and identify the premature acceptance. Confirm the
    thread returns to the same retry worker, which removes the sentence,
    records that it was the seeded stimulus rather than evidence, reruns
    validation, pushes the correction, and resolves the thread. A later `+1`
    on the corrected revision is a successful clean review and must not be
    treated as a continuation failure. If the seeded revision receives no
    actionable finding, record the review stimulus as inconclusive; do not
    misclassify an otherwise correct final revision's `+1` as an AO failure.
11. Confirm required GitHub checks pass and auto-merge remains off. A human may
    then merge the canary pull request. Move the Linear issue to `done` only
    after merge, and confirm reconciliation releases the run and terminates or
    retires remaining workflow ownership without another retry.

If the canary must be abandoned, move the issue to `cancelled` and require the
same terminal cleanup evidence.

The operator may deliberately perform the label, state, service-restart, and
worker-termination actions above. Any additional human relay needed to preserve
claim identity, schedule retry, discover review feedback, or resume the worker
fails the corresponding acceptance criterion.

## Risks and Stop Conditions

- A duplicate claim, overlapping attempt, concurrency above one, unbounded
  retry, or dispatch without the required label is an immediate rollback.
- A missing or incorrect canary assignee, a missing dispatch-time pause marker,
  or repository mutation before the exact release message stops the canary.
- Loss of the accepted project configuration during enablement or rollback is
  an immediate rollback using the last verified configuration.
- A worker credential leak, product or skill diff, unauthorized tracker write,
  unexpected merge, or auto-merge enablement stops the canary.
- A daemon restart that loses issue ownership, or review feedback that needs a
  human to find or route it, fails the relevant acceptance row.
- A passing canary proves only this repository, Linear project, AO build, and
  host configuration. Wider enrollment requires a separate decision.
