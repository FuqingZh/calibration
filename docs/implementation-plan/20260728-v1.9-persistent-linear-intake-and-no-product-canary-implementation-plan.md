# v1.9 Persistent Linear Intake and No-product Canary Implementation Plan

Date: 2026-07-28

Status: pending live canary

Issue: FUQ-14

## Goal

Opt `calibration` into one persistent, project-scoped Linear Symphony lane and
use one controlled documentation-only issue to establish whether the deployed
AO service can claim, recover, retry, reconcile, continue review work, and
observe Linear progress without enabling auto-merge.

The repository contract is durable after this plan and `WORKFLOW.md` merge.
Operational acceptance remains pending until the live canary produces the
evidence below.

## Non-goals

- Do not change skills, behavioral evaluations, AO binaries, the accepted
  service deployment, credentials, or host permission defaults.
- Do not add workflow hooks. The installed AO intake lane does not execute
  repository lifecycle hooks, so declaring them would create a false runtime
  contract.
- Do not enroll another repository or Linear project.
- Do not give the tracker adapter write authority or place a Linear credential
  in the repository or worker configuration.
- Do not change product code during the canary.
- Do not enable auto-merge or authorize AO to merge a pull request.
- Do not describe the lane as accepted, production-proven, or generally
  reusable before the live canary passes.

## Ownership Boundaries

- Root `WORKFLOW.md` owns issue eligibility, the Linear project UUID, normalized
  active and terminal states, the 30-second polling interval, the one-agent
  concurrency ceiling, and the worker prompt.
- `AGENTS.md` and `README.md` own repository setup, validation, delivery, and
  installer safety. The workflow prompt delegates to those authorities instead
  of copying their commands.
- This plan owns rollout order, canary evidence, acceptance, and rollback.
- AO's accepted user service owns persistent polling, durable claims,
  reconciliation, retry scheduling, isolated worktrees, and review
  continuation.
- Linear owns issue labels and state. A human canary operator owns deliberate
  label and state transitions; the AO tracker adapter remains read-only.
- The task worker owns the implementation branch, repository validation,
  commits, push, and pull-request updates.
- GitHub Actions and Automatic Codex Review own remote mechanical and review
  feedback. The user retains merge and risk authority.
- Host configuration and the Linear credential remain outside Git. This pull
  request records commands but does not execute the rollout.

## Rollout Preconditions

Do not enable intake until all of these are true:

1. The FUQ-14 pull request is merged by a human and `origin/main` contains the
   reviewed `WORKFLOW.md` and this plan.
2. `ao status --json` reports `health: "ok"` and `ready: "ready"`.
3. `ao doctor --json` reports zero failures.
4. `ao project get calibration --json` still reports the accepted repository
   path, `main` default branch, Codex worker, isolated `CODEX_HOME`, and
   `bypass-permissions`.
5. The Linear credential remains outside Git and the active daemon retains the
   accepted Linear credential wrapper and worker-environment filtering.
6. No other `calibration` intake canary or workflow-owned agent is active.
7. Auto-merge is off.

Failure of any precondition leaves intake disabled.

## Slice 3: Controlled No-product Canary

Create one Linear issue in the configured project whose only repository change
is to append a canary evidence and closeout section to this plan. The issue must
name the expected validation contract, forbid product, skill, evaluation,
runtime, host-configuration, credential, and auto-merge changes, and require a
ready-for-review pull request that remains unmerged until human approval.

Use this controlled sequence:

1. Create the issue in normalized `open` without `AO Intake`. Wait at least two
   complete 30-second polling intervals and confirm AO creates no claim,
   session, branch, or pull request.
2. Add `AO Intake`. Record the issue UUID and identifier, workflow revision,
   claim record, owning session, worktree, branch, and first attempt. Confirm
   there is exactly one claim and at most one workflow agent.
3. Before repository edits, instruct the first worker to finish a read-only
   inspection and wait. Restart only the AO user service, then read back the
   same durable issue claim and owning session. Confirm restart creates no
   duplicate session or attempt.
4. Terminate that waiting worker through AO to exercise abnormal-exit retry.
   Observe the durable run become retry-queued, then claimed as the next
   attempt after its bounded backoff. Confirm the issue identity and workflow
   revision are retained and never overlap with another active attempt.
5. Move the Linear issue deliberately from normalized `open` to
   `in_progress`. Confirm the read-only adapter observes the state and the
   retry worker continues the same task rather than creating another claim.
6. Let the retry worker make only the planned documentation closeout change,
   run the full repository validation contract, commit, push, and open a
   ready-for-review pull request.
7. Move the Linear issue to normalized `review`. Confirm reconciliation keeps
   the owning worker available and does not create a replacement.
8. Submit one actionable Automatic Codex Review finding. Confirm it returns to
   the same retry worker, which implements the bounded correction, reruns
   validation, pushes the update, and resolves the review thread.
9. Confirm required GitHub checks pass and auto-merge remains off. A human may
   then merge the canary pull request. Move the Linear issue to `done` only
   after merge, and confirm reconciliation releases the run and terminates or
   retires remaining workflow ownership without another retry.

If the canary must be abandoned, move the issue to `cancelled` and require the
same terminal cleanup evidence.

The operator may deliberately perform the label, state, service-restart, and
worker-termination actions above. Any additional human relay needed to preserve
claim identity, schedule retry, discover review feedback, or resume the worker
fails the corresponding acceptance criterion.

## Acceptance Matrix

| Capability | Required live evidence |
| --- | --- |
| Claim | No dispatch without `AO Intake`; one durable claim after labeling; one workflow agent maximum. |
| Restart | Service restart retains the issue claim and owning session without a duplicate attempt. |
| Retry and reconciliation | Abnormal worker termination produces one bounded retry with retained issue and workflow identity; state or label ineligibility prevents further dispatch; terminal state releases ownership. |
| Review continuation | One actionable review finding reaches the same post-retry worker, which pushes a validated correction and resolves the thread. |
| Linear progress | Recorded readback observes `open` to `in_progress` to `review`, then `done` after human merge, or `cancelled` on rollback. |
| Pull-request delivery | The documentation-only canary PR is ready for review, repository validation and required checks pass, and the final diff stays inside the declared no-product boundary. |
| Auto-merge off | GitHub readback shows auto-merge disabled before review, after the correction, and at terminal acceptance. |

Every row must pass. Static workflow parsing, daemon health, a created worker,
or a successful pull request alone is insufficient.

Rollback is a configuration change, not deletion of the repository contract or
credential. First remove `AO Intake` from the canary issue or move it to
`cancelled`, and wait for AO to release active workflow ownership. Then restore
the accepted non-intake project configuration:

```bash
ao project set-config calibration --config-json '{

  "sessionPrefix": "calibration",
  "env": {

  },
  "agentConfig": {},
  "worker": {
    "agent": "codex",
    "agentConfig": {
      "permissions": "bypass-permissions"
    }
  },
  "orchestrator": {
    "agentConfig": {}
  },
  "trackerIntake": {}
}' --json
ao project get calibration --json
ao status --json
ao doctor --json
```

Readback must show an empty or disabled `trackerIntake`, the unchanged accepted
worker configuration, a ready daemon, and zero doctor failures. Verify no
workflow-owned `calibration` session remains active and no new claim appears
for at least two complete 30-second polling intervals.

Do not delete or revoke the Linear credential during ordinary rollback. Service
or credential rollback remains owned by the current-host AO runbook and
requires separate authorization.

## Risks and Stop Conditions

- A duplicate claim, overlapping attempt, concurrency above one, unbounded
  retry, or dispatch without the required label is an immediate rollback.
- Loss of the accepted project configuration during enablement or rollback is
  an immediate rollback using the last verified configuration.
- A worker credential leak, product or skill diff, unauthorized tracker write,
  unexpected merge, or auto-merge enablement stops the canary.
- A daemon restart that loses issue ownership, or review feedback that needs a
  human to find or route it, fails the relevant acceptance row.
- A passing canary proves only this repository, Linear project, AO build, and
  host configuration. Wider enrollment requires a separate decision.

## Final Verification and Closeout

The canary pull request appends exact timestamps, issue and session identities,
workflow revision, attempt transitions, commands, validation results, review
thread and check readback, Linear state progression, auto-merge readback, and
terminal cleanup to this plan. Do not record credentials or secret-bearing
environment output.

After all acceptance rows pass, change this plan's status to
`accepted for calibration`. If any row fails, record the first failed gate,
rollback evidence, and status `rejected` or `pending retry`. Preserve the
repository's existing outcome-autonomy guidance in either result.
