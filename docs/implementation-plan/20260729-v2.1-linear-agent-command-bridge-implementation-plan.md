# Linear Agent command bridge implementation plan

Date: 2026-07-29

Status: In progress; Slice 0 started

Supersedes
`20260728-v2.0-three-scenario-linear-acceptance-implementation-plan.md` for all
unexecuted Linear intake and acceptance work.

## Goal

Replace state-driven Linear intake with an explicit, idempotent command path:

1. a user delegates an issue to a private Linear AO Agent or uses an accepted
   dispatch mention;
2. a thin bridge validates that AgentSession event and creates exactly one AO
   session through AO's existing API;
3. AO owns execution, retry, PR observation, review continuation, and
   termination; and
4. the bridge projects verified AO facts into Linear without using projected
   state as a future dispatch signal.

The completed path must reuse Linear's Agent and webhook platform and AO's
native session and SCM loop. It must not introduce a second scheduler.

## Settled design

The owning decision is
[`2026-07-29-linear-projection-and-explicit-agent-dispatch.md`](../decisions/2026-07-29-linear-projection-and-explicit-agent-dispatch.md).

The critical invariants are:

- only a new, authorized Linear AgentSession can originate a Linear-side
  dispatch;
- issue state, labels, assignees, links, and GitHub events never dispatch;
- one Linear AgentSession creates at most one AO session;
- a new run generation requires a new AgentSession;
- AO remains the execution and retry authority;
- the bridge stores integration idempotency, not scheduling state;
- Linear credentials never enter AO or worker environments; and
- auto-merge remains disabled.

## Affected components

| Component | Ownership and intended change |
| --- | --- |
| `calibration` documentation | Record the failed state-driven assumption, current authority, implementation gates, and live acceptance evidence. |
| New private `ao-linear-agent-bridge` repository | Standalone TypeScript service using the official Linear SDK, a small SQLite integration ledger, and AO's loopback HTTP API. |
| Linear private Agent application | App actor, delegation/mention scopes, AgentSession events, signing secret, and team access. |
| Current AO user service | Remains the session and SCM controller; keeps tracker intake disabled. |
| `agent-orchestrator` fork | No bridge implementation. Remove the fork-only Linear tracker adapter and credential plumbing only after replacement canary acceptance. |

The bridge is separate because its public webhook and OAuth trust boundary must
not expose or enlarge AO's loopback API. It passes the deletion test by owning
four contracts absent from both products: local authorization, delivery
deduplication, AgentSession-to-AO mapping, and deployment-specific projection.

## Non-goals

- Linear Coding Sessions or Linear-hosted code execution.
- A generic workflow engine or Symphony-compatible scheduler.
- Issue-state, label, or assignee polling.
- A public AO API, remote AO dashboard, or direct database access.
- Linear-side cancellation or retry in version 1.
- Automatic merge or risk acceptance.
- Broad repository enrollment.

## External prerequisites

The following are required only when their owning slice is reached:

- a private Linear OAuth application installed by a workspace administrator
  with the minimum app actor, assignable, mentionable, AgentSession, and
  mutation scopes;
- one controlled public HTTPS endpoint that forwards only the bridge webhook
  route;
- a secret store available only to the bridge service; and
- explicit mappings for allowed Linear organization/team, app actor, Linear
  workflow-state UUIDs, and AO project IDs.

The endpoint provider is an environment dependency, not an application
contract. No production deployment begins until its TLS, request-body
preservation, and rollback behavior are read back.

## Slice 1: freeze and test the Developer Preview contract

### Repository

Create the private `ao-linear-agent-bridge` repository only after fixture
review. Use TypeScript and the official Linear SDK; do not copy SDK signature
or GraphQL implementations.

### Contracts and fixtures

Define typed fixtures for:

- a valid AgentSession `created` event from delegation;
- the verified mention-created AgentSession shape, if Linear emits one in the
  configured preview;
- a duplicate delivery UUID;
- a second delivery for the same AgentSession;
- an ordinary `Issue` state update;
- an event from an unapproved team or app actor;
- an invalid signature;
- an expired timestamp; and
- an AgentSession for an issue already mapped to an active AO run.

The contract-test server verifies the exact raw request body. It acknowledges a
valid AgentSession without calling AO. The fixture source, schema observation
date, and redacted payload hash are recorded.

### Acceptance

- valid delegation event returns success within Linear's response window;
- duplicate delivery and duplicate AgentSession are deterministic no-ops;
- invalid signature, stale timestamp, and wrong scope are rejected;
- every ordinary Issue event produces zero dispatch calls; and
- no external Linear or AO write occurs in this slice.

If the real Developer Preview event cannot distinguish a deliberate dispatch
from an ordinary mention, version 1 accepts delegation only. Do not add prompt
classification or model judgment to repair the protocol.

## Slice 2: implement idempotent dispatch

### Interfaces

The bridge owns:

```text
POST /webhooks/linear-agent
LinearAgentSessionID -> AOSessionID
LinearDeliveryID -> processed result
AOProjectMapping(linear team/project -> AO project)
```

The SQLite integration ledger contains:

- `linear_deliveries`: delivery UUID, received timestamp, validation outcome;
- `agent_runs`: AgentSession ID, issue ID, AO project ID, AO session ID,
  generation, state, and timestamps; and
- `projection_effects`: stable effect key, target, outcome, and timestamp.

It contains no retry due time, worker lease, claim state, or scheduling queue.

### Behavior

1. Read and verify the raw webhook body, signature, and timestamp.
2. Check organization, team, app actor, and AO project allowlists.
3. Insert the delivery UUID atomically.
4. Resolve the AgentSession:
   - return the existing mapping when it is already known;
   - return the active issue mapping when an AO run is still live; or
   - reserve a new generation for a terminal issue mapping.
5. Acknowledge Linear promptly.
6. Asynchronously call AO's existing session-spawn API.
7. Atomically bind the AO session result to the AgentSession.
8. On an ambiguous AO timeout, read back before retrying; never blind-spawn.

### Acceptance

- 100 concurrent copies of one delivery create one ledger row and one AO spawn;
- distinct deliveries for one AgentSession create one AO spawn;
- bridge restart preserves the result;
- a transient AO failure cannot create an unbound duplicate;
- an active issue re-delegation returns the existing run;
- after terminal completion, a new AgentSession creates exactly generation 2;
  and
- an issue state transition creates zero AO sessions.

## Slice 3: project AO facts into Linear

### Behavior

The bridge observes only AO sessions it created. It uses supported AO read APIs
and bounded backoff; it does not read AO SQLite.

Configured effects are:

- session bound: AgentSession acknowledgement, AO identity, In Progress;
- PR ready: PR external URL and In Review;
- AO-managed retry: activity update on the same AgentSession and generation;
- accepted merge completion: Done;
- explicit AO cancellation: Canceled; and
- unrecoverable failure: failure activity and configured blocked state when
  available.

Every effect has a stable idempotency key. Linear write failure queues only the
projection effect; it never retries dispatch. Issue webhooks caused by these
writes are ignored by the dispatch path.

### Acceptance

- each AO fact produces at most one Linear mutation;
- projection resumes after bridge restart;
- a Linear write outage does not affect the AO run;
- a projected In Progress or In Review state cannot create a session;
- late PR merge cannot overwrite an explicit canceled terminal mapping; and
- Linear tokens remain absent from AO daemon and fresh worker environments.

## Slice 4: controlled live handshake and canary

### Gate A: no-side-effect handshake

- Install the private app for one team.
- Delegate one disposable issue.
- Read back a valid AgentSession event and acknowledgement.
- Keep AO dispatch disabled.

Gate A passes only when the real event matches the tested contract and duplicate
delivery is harmless.

### Gate B: dispatch canary

Enable one AO project mapping and run:

1. delegation creates exactly one AO worker;
2. webhook redelivery creates no replacement;
3. changing Linear between Todo, In Progress, Canceled, and In Progress creates
   no worker;
4. the worker opens one pull request;
5. actionable review reaches and is addressed by the owning AO worker;
6. merge produces one Done projection;
7. explicit AO cancellation followed by a late merge remains canceled; and
8. a fresh delegation after terminal state creates exactly generation 2.

Record Linear AgentSession, issue, AO session, generation, PR, review thread,
terminal AO state, and final Linear state.

No broader project mapping or unattended dispatch is enabled until every gate
passes.

## Slice 5: retire fork-only Linear intake

After Slice 4 acceptance:

- preserve the current AO binary, database, unit, wrapper, and config in one
  dated rollback set;
- remove the fork-only Linear tracker adapter and provider-specific CLI/config
  surface while retaining upstream GitHub intake behavior;
- remove the daemon Linear API-key wrapper and service drop-in;
- verify AO starts without Linear credentials and existing sessions survive;
- keep bridge credentials in the bridge service only;
- update the AO fork against a pinned upstream revision and run its complete
  validation;
- update calibration docs and close the superseded v1.9/v2.0 route; and
- leave auto-merge disabled.

Deletion occurs in a separate PR so the accepted bridge can be retained if the
cleanup patch is rejected.

## Verification matrix

| Contract | Deterministic gate | Live gate |
| --- | --- | --- |
| Explicit dispatch only | Issue-event fixtures yield zero AO calls | Manual state drift yields zero sessions |
| Delivery idempotency | concurrent duplicate test | webhook redelivery readback |
| AgentSession idempotency | distinct deliveries, same session | one Linear session, one AO session |
| New generation | terminal mapping plus new AgentSession | explicit re-delegation creates generation 2 |
| AO authority | no bridge retry/lease schema | AO owns abnormal worker retry |
| Review continuation | existing AO integration tests | actionable current-head review correction |
| Projection idempotency | stable effect-key tests | one PR link and one terminal state |
| Cancellation wins | late-merge fixture | canceled canary remains canceled |
| Secret isolation | environment construction test | daemon and fresh-worker name-only checks |
| Recovery | bridge restart tests | service restart with unchanged mappings |

## Rollback

Before Slice 4, rollback means stop or disable the bridge and remove the private
Agent delegation from the disposable issue. Tracker intake remains disabled,
so no legacy path resumes.

After Slice 4 but before Slice 5, stop the bridge and preserve its ledger; AO
continues existing sessions independently. Do not re-enable tracker intake.

After Slice 5, restore only the complete pinned AO rollback set if an AO
regression requires it. Restoring the old binary does not authorize restoring
state-driven Linear intake. App revocation and credential deletion are explicit
security operations, not incidental rollback steps.

## Delivery sequence

Use independently reviewable changes:

1. calibration decision, plan, authority-map update, and v2.0 failure record;
2. bridge contract fixtures and signature/authorization tests;
3. idempotent dispatch ledger and AO client;
4. projection and recovery behavior;
5. live canary evidence; and
6. AO fork cleanup and deployment closeout.

For every repository, run its complete local validation, open a pull request,
read back CI and review state at the current head, and keep merge under user
authority.
