# Three-scenario Linear acceptance implementation plan

Date: 2026-07-28

Status: In progress; Slice 1 is
[`FuqingZh/agent-orchestrator#12`](https://github.com/FuqingZh/agent-orchestrator/pull/12)

Supersedes:
`20260728-v1.9-persistent-linear-intake-and-no-product-canary-implementation-plan.md`
for all unexecuted canary and acceptance work.

## Goal

Accept or reject the current AO + Linear delivery loop with three observable
state-machine scenarios:

1. issue intake continues through pull-request review and merge;
2. an abnormal worker exit continues the same issue through one durable retry;
3. issue cancellation releases the worker, and a later pull-request merge does
   not erase the cancellation result.

The acceptance contract measures outcomes and durable transitions. It does not
require a second probe issue, pause barriers, repeated unlabeled dwell windows,
or manual orchestration between every transition.

## Corrected ownership

- AO's Linear adapter is read-only. It observes issue state, claims work,
  reconciles workers, and records a durable terminal reason.
- The worker and configured Linear/GitHub integration own remote issue writes.
  AO must not be given Linear mutation authority to compensate for an
  integration rule.
- AO's SCM observer owns PR, CI, and review observations and delivers actionable
  feedback to the owning worker.
- The AO user service owns persistence across shell and Codex task lifetimes.
  An ad-hoc daemon process is not acceptable deployment evidence.
- The user retains merge and risk authority. Auto-merge remains out of scope.

If merging a PR changes a previously canceled Linear issue to Done, that is a
Linear/GitHub integration failure. Fix the integration rule and repeat scenario
3; do not add a competing AO write.

## Existing evidence retained

The v1.9 run established useful facts that do not need to be replayed:

- project-scoped, label-gated Linear intake can claim one issue;
- the daemon credential is read-only and absent from ordinary worker
  environments;
- durable workflow-run rows survive restart;
- issue state and eligibility are reconciled;
- the repository validation and installer contracts remain intact.

The v1.9 manual sequence did not establish a stable review continuation or a
clean cancellation-versus-late-merge boundary. Those claims are replaced by
the deterministic gates and three live scenarios below.

## Non-goals

- Full Symphony conformance.
- Four-way or cross-project concurrency testing.
- A read-only probe issue.
- Repeating credential, permission, or installer evidence already accepted.
- Daemon-side Linear mutations.
- Product-code changes in calibration.
- Auto-merge, bulk repository enrollment, or unattended production rollout.

## Slice 1: Land deterministic state-machine gates

In the AO fork, add only the missing cross-component regression coverage:

- a canceled Linear issue normalizes to `cancelled`;
- an unresolved review comment passes through SCM observer, SQLite persistence,
  lifecycle reduction, and the owning worker messenger;
- an active issue whose worker exits continues under the existing durable
  retry smoke;
- a canceled Linear issue terminates its worker and releases its workflow run
  as `terminal:cancelled`;
- a later AO PR-merge observation cannot reopen or rewrite that released run.

Focused gate:

```bash
cd backend
GOCACHE="$(mktemp -d)" go test ./internal/adapters/tracker/linear
GOCACHE="$(mktemp -d)" go test ./internal/integration \
  -run 'TestSCMObserverEndToEnd|TestWorkflowIntakeLinearCancellationIsTerminalAndSurvivesLatePRMerge|TestWorkflowIntakeSQLiteRestartAndContinuationSmoke' \
  -count=1
```

Then run the AO repository's complete validation contract. This slice passes
only after its PR is merged and fork `origin/main` resolves to the merge
commit.

## Slice 2: Restore the exact persistent canary

Build the merged AO fork revision reproducibly using the existing Phase 3
runbook, install it through the accepted wrapper, and restart the real
`agent-orchestrator.service`. Do not substitute a shell-owned daemon.

Acceptance:

- `systemctl --user is-active agent-orchestrator.service` reports `active`;
- `systemctl --user show agent-orchestrator.service` identifies the accepted
  wrapper and merged AO revision;
- `ao status --json` reports `ready` or `running`;
- `ao doctor --json` reports zero failures;
- `ao project get calibration --json` retains the exact Linear project,
  assignee, workflow path, worker, permission, and bot-review allowlist;
- the installed binary hash is recorded against the merged source revision.

Any stale run file, missing service, or shell-lifetime daemon blocks live
acceptance.

## Slice 3: Run exactly three live scenarios

Use three disposable Linear issues in the existing private project, one at a
time. Each starts with the exact assignee and `AO Intake` label. Record only
issue ID, session ID, workflow-run state and attempt, PR URL/head, relevant
review delivery, and final issue/run state.

### Scenario A: review-to-merge completion

1. Create a small documentation-only issue and make it eligible.
2. Observe one durable claim and one owning worker.
3. Let the worker open a ready-for-review PR.
4. Add one actionable review comment on the current head.
5. Without `ao send`, observe a new worker turn that addresses the comment and
   updates the same PR.
6. After checks and current-head review pass, the user merges the PR.
7. Confirm the worker/session completes, the workflow run releases with the
   observed terminal state, and the Linear issue reaches the configured
   completed state.

Seeing text pasted in a pane is insufficient; the worker must start the
continuation turn.

### Scenario B: abnormal-exit continuation

1. Create a small issue whose work remains active.
2. After the first worker is bound, terminate only its managed agent process.
3. Observe one retry on the same canonical issue and workflow run.
4. Confirm the attempt increases, exactly one replacement worker is active,
   and the replacement prompt retains the issue identity.
5. Cancel the disposable issue and confirm cleanup.

Do not restart the daemon in this scenario; it tests worker retry, not service
deployment.

### Scenario C: cancellation wins over a late merge

1. Create an eligible issue and allow its worker to open a disposable PR.
2. Move the Linear issue to Canceled.
3. Before merging the PR, wait until AO records `released` with
   `terminal:cancelled` and terminates the worker.
4. Merge the already-open PR as a deliberate late event.
5. Confirm the AO workflow run remains `released` with
   `terminal:cancelled` and the Linear issue remains Canceled.

If step 5 fails only in Linear, classify it as Linear/GitHub integration drift,
repair that integration, and repeat scenario C. AO passes its boundary only if
its durable run remains unchanged.

## Slice 4: Close or roll back

Accept persistent intake only when all three scenarios pass against the exact
merged and service-managed AO revision. Record a compact result table in this
plan with scenario, issue, session/attempt, PR, final AO run, final Linear
state, and pass/fail.

On failure:

- disable `trackerIntake.enabled` for `calibration`;
- read back the disabled configuration;
- leave the Linear credential and accepted service wrapper unchanged unless a
  separate security issue requires revocation;
- preserve the three scenario artifacts and name the failing owner: AO,
  Linear/GitHub integration, GitHub review, or host service.

Before delivering the calibration closeout:

```bash
pdm lock --check
pdm run check
CODEX_HOME="$(mktemp -d)" bash install.sh --dry-run
git diff --check
git diff --cached --check

```

The result is accepted only when the AO PR is merged, the service is persistent
and healthy, all three live scenarios pass, and the calibration documentation
records the exact evidence without reintroducing the retired manual sequence.
