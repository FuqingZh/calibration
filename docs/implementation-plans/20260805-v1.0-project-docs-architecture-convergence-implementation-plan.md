# Project Docs Architecture Convergence Implementation Plan

Version: v1.0

## Goal

Converge the cross-project `docs/` guidance on clear directory roles, mature
technical-documentation terminology where it applies, thin local contracts,
and explicit lifecycle rules.

The result should reduce duplicated writing guidance without making external
web pages a silently changing source of local policy.

## Settled Direction

The preferred greenfield layout is:

```text
docs/
  README.md
  architecture/
  decisions/
  implementation-plans/
  testing/
  benchmarks/
  tutorials/
  how-to-guides/
  runbooks/
  compatibility/
  assets/
  archive/
```

Do not create empty directories to match this layout. `docs/README.md` is
required when `docs/` exists. Every other directory is created only when its
content trigger exists.

Directory roles are:

- `architecture/`: current system facts, boundaries, data flow, and active
  contracts.
- `decisions/`: settled high-impact choices, alternatives, rationale,
  consequences, and reopening conditions.
- `implementation-plans/`: implementation slices, dependencies, migrations,
  risks, verification, and acceptance.
- `testing/`: durable test strategy, quality gates, smoke and real-data
  validation, and acceptance criteria.
- `benchmarks/`: reproducible measurement protocols, environments, baselines,
  output validation, and results.
- `tutorials/`: guided learning experiences that help a reader acquire a new
  capability.
- `how-to-guides/`: task-oriented guidance that helps a competent reader
  achieve and verify one concrete outcome.
- `runbooks/`: controlled operational procedures with prerequisites,
  verification, recovery, rollback, and escalation.
- `compatibility/`: empirically verified constraints, deviations, failure
  signatures, and safe adaptations at opaque external or third-party
  boundaries.
- `assets/`: repository-owned images, diagrams, and editable sources referenced
  by documentation.
- `archive/`: superseded material retained for traceability and excluded from
  current authority unless a current document explicitly cites it.

## Naming Decisions

- Prefer `docs/decisions/`. ADR is a mature document type, but the ADR ecosystem
  does not mandate one directory spelling.
- Prefer `implementation-plans/` over singular `implementation-plan/` because
  the directory is a collection. This is a clarity decision, not a claimed
  industry standard.
- Prefer `tutorials/` over `learning/`, following the learning-oriented
  terminology in [Diataxis tutorials](https://diataxis.fr/tutorials/).
- Prefer `how-to-guides/` over `cookbook/`, following the goal-oriented
  terminology in
  [Diataxis how-to guides](https://diataxis.fr/how-to-guides/).
- Prefer `compatibility/` over `field-manual/` when the intended subject is
  stable knowledge learned at external black-box boundaries. This is a clear
  domain name, not a universal repository-layout standard.
- Keep `architecture/`, `testing/`, `benchmarks/`, `runbooks/`, `assets/`, and
  `archive/`.

## External Method Boundary

Use established external methods for general authoring guidance and keep a
thin local adapter that defines selection, adopted invariants, repository
requirements, precedence, and completion.

External references include:

- [Diataxis tutorials](https://diataxis.fr/tutorials/) and
  [how-to guides](https://diataxis.fr/how-to-guides/);
- [Architectural Decision Records](https://adr.github.io/) and
  [MADR templates](https://adr.github.io/adr-templates/);
- [AWS runbook guidance](https://docs.aws.amazon.com/wellarchitected/2023-10-03/framework/ops_ready_to_support_use_runbooks.html);
- compatibility-policy examples such as the
  [Kubernetes version skew policy](https://kubernetes.io/releases/version-skew-policy/)
  and
  [MDN compatibility data](https://developer.mozilla.org/en-US/docs/MDN/Writing_guidelines/Page_structures/Compatibility_tables).

External sources provide the broader method. Calibration owns the locally
adopted minimum contract. Repository-local documentation owns project facts,
commands, versions, and executable validation. An external page change does
not alter local policy until the change is explicitly reviewed and adopted.

Do not copy large external guides into calibration. Keep enough locally that
document selection and minimum acceptance remain usable if an external link is
temporarily unavailable.

## Thin Document-Type Contract

Use this default shape where it is sufficient:

```text
Use When
Method Reference
Local Requirements
Complete When
```

`Do Not Include` is not a required section. Put common selection boundaries in
the document-type router. Keep a short negative boundary only when it prevents
a material authority, risk, lifecycle, or repeated-classification failure.

Examples of central routing boundaries:

```text
guided capability acquisition       -> tutorial
one concrete ordinary task          -> how-to guide
controlled or high-risk operation   -> runbook
opaque external compatibility rule  -> compatibility record
current system truth                -> architecture overview
settled consequential choice        -> decision record
decision-complete execution path    -> implementation plan
```

For compatibility material, retain one strong boundary: raw trial-and-error
belongs in `.traces/`; only repeatedly verified external behavior and reusable
rules are promoted into `docs/compatibility/`.

## Scope And Non-Goals

This plan covers the cross-project documentation contract and the calibration
repository changes needed to keep that contract self-consistent.

It does not yet:

- implement, install, or claim behavioral validation for a future `teach`
  skill;
- change `grilling` or introduce a numeric confidence threshold;
- bulk-migrate documentation in sibling repositories;
- classify every existing file under `proteomics/docs/field-manual/`;
- claim that `implementation-plans/` or `compatibility/` is an externally
  standardized directory path;
- create empty optional directories.

The accepted `teach` direction is a dependent implementation slice. It starts
from this documentation model, keeps personal teaching state separate from
team authority, and does not enter the installer until its local behavior and
validation evidence are accepted.

## Slice 2: Converge Document-Type Routing

Update `references/engineering/docs/document-types/README.md` as the central
selection router.

Update existing contracts where necessary:

- `decision-record.md` prefers `docs/decisions/`;
- `implementation-plan.md` prefers `docs/implementation-plans/`;
- existing types use positive selection and completion language;
- repeated exclusions move to the router unless they prevent a material
  failure.

Add thin contracts only for distinct reusable document types:

- `tutorial.md`;
- `how-to-guide.md`;
- `test-plan.md`;
- `benchmark-record.md`;
- `runbook.md`;
- `compatibility-record.md`.

Do not add document types for `assets/` or `archive/`. Assets are supporting
resources. Archive is a lifecycle state, and archived documents retain their
original type.

Acceptance:

- the router distinguishes every neighboring type without loading all type
  files;
- tutorial and how-to contracts link to Diataxis and repeat only local
  requirements;
- external links are methodological references rather than live policy
  imports;
- no type contains boilerplate exclusions merely for structural symmetry.

## Slice 6: Establish The Teach Upstream Baseline And Local Contract

Treat `teach` as an explicitly invoked, user-specific interactive teaching
mode. It may read current project code and authoritative documentation as
teaching context, but the engineering repository is read-only teaching context
by default. Persistent teaching state belongs only in a personal learning
workspace that the user explicitly selects, preferably a dedicated directory
or repository. The skill source directory is never the teaching workspace. If
no personal learning workspace is selected, offer session-only teaching with no
filesystem writes. Personal missions, preferences, mastery records, and
session notes do not become team project documentation.

Only an explicit request to make the result durable starts project-document
routing. Route the promoted, team-neutral result by its primary role:

- a guided learning path from a starting state to a capability -> tutorial;
- instructions for completing one known task -> how-to guide;
- stable current system structure or concepts -> architecture;
- verified external or third-party black-box behavior -> compatibility record;
- a controlled or high-risk operating procedure -> runbook.

Adopt Matt Pocock's `teach` through the existing third-party provenance model:

1. Pin the exact upstream commit used for implementation.
2. Import the complete referenced `teach` source tree unchanged into
   `thirdparty/skills/teach/` in a standalone vendor commit.
3. Record the repository, source path, imported commit, and checked upstream
   commit in `thirdparty/sources.tsv`.
4. Preserve the upstream MIT copyright and permission notice with the vendored
   source.
5. Do not add the unchanged import to `MANAGED_THIRDPARTY_SKILLS` or otherwise
   install it.
6. Apply the local behavior changes in a separate commit and record them in
   `thirdparty/PATCHES.md`.
7. Add focused behavior cases and run a stated representative evaluation.
8. Add `teach` to the installer only after its contract and evidence are
   accepted.

The local patch should retain the upstream mission grounding, trusted-source
research, small learning units, retrieval practice, and tight feedback loop.
It should remove the assumption that the current project directory is a
personal learning workspace and replace it with explicit workspace selection.
Preserve learner-specific files and HTML lessons inside that selected
workspace, while keeping the current engineering repository and skill source
read-only. Require an explicit persistence request before entering the project
documentation workflow.

The adaptation should also close the material gaps found in the upstream audit:

- distinguish the selected learning-workspace root from the installed skill
  source before reading templates or writing state;
- assess the learner's mission and current capability before creating the first
  lesson, reusing existing learning records on later sessions;
- verify time-sensitive material from current primary or authoritative sources
  and retain enough source context to revisit it;
- randomize quiz answer position at render or interaction time rather than
  relying on wording alone; and
- make review cadence, lesson stopping conditions, and session resumption
  explicit without claiming an automatic spaced-repetition scheduler.

Keep the active skill under `thirdparty/` while the upstream teaching protocol
remains its recognizable core. If the accepted implementation replaces that
core rather than adapting it, create a first-party `skills/teach` instead and
retain the immutable upstream provenance and applicable license notices. Do
not disguise a locally owned skill as a lightly patched vendor import.

Acceptance:

- the untouched upstream baseline and local behavioral delta are independently
  reviewable;
- the original upstream behavior is never installed as an intermediate runtime
  state;
- default teaching produces no writes to the current engineering repository or
  the installed skill source;
- persistent learner state is confined to an explicitly selected personal
  learning workspace, while session-only teaching produces no filesystem
  writes;
- durable promotion requires an explicit user request and follows the project
  document router;
- learner-specific state is excluded from team-authoritative documentation;
- representative evaluation covers initial assessment, cross-session resume,
  current-source grounding, workspace isolation, session-only no-write
  behavior, quiz answer-position resistance, explicit promotion, and
  neighboring document-type routing.
