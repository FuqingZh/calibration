Date: 2026-08-24
Status: stopped after S5 rejection; S0--S3 baseline is frozen, S4 activation is
implemented, the valid S5 smoke rejected the candidate, and S6--S7 remain

## Goal

Turn proportional validation from a general instruction into observable runtime
behavior. For each repository change, the agent must derive the smallest honest
check from the completion claim, affected seam, repository-owned contracts, and
available evidence. It must broaden only when a narrower check cannot discharge
an obligation or a more specific rule explicitly requires the broader gate.

The intended outcome is precise validation, not uniformly less validation:

- an ordinary contract-preserving documentation edit selects documentation,
  link, formatting, or diff checks that exercise that edit;
- a generated document selects its generator and final-artifact checks;
- a skill, prompt, policy, or workflow edit selects structural checks plus a
  representative behavioral check;
- a leaf implementation edit selects the affected test seam;
- a shared or compatibility-sensitive contract selects its consumer or
  compatibility checks; and
- the complete canonical gate remains required when an explicit local rule or
  the changed validation, generation, build, dependency, or compatibility seam
  makes it the smallest honest check.

## Baseline And Root Cause

The v1.0 increment aligned the shared principle, global template, repository
navigation, and one docs-only prompt around proportional validation. Its result
explicitly established contract consistency and installer propagation, not a
behavioral improvement.

Three gaps still explain the observed full-gate expansion:

1. The global wording names proportionality but does not require a claim-to-seam
   proof procedure or a reason for excluding broader checks. A canonical
   repository entrypoint can therefore become a convenient default even when it
   does not add relevant evidence.
2. `$calibration` currently triggers for broad durable engineering
   documentation. That loads a cross-project judgment workflow for ordinary
   repository prose and increases the chance that validation grows beyond the
   affected surface.
3. Repository-local `AGENTS.md` files are more specific authority. Earlier
   copied rules that unconditionally require a complete gate correctly override
   a newer global default until each owning repository is migrated. Changing
   calibration alone cannot safely bypass them.

Static prompt and wording tests cannot decide whether an agent actually chose a
focused check, ran an unnecessary runtime gate, obeyed a local hard mandate, or
made an unsupported completion claim. This plan therefore freezes executable
selection fixtures before changing runtime instructions.

### Smallest Honest Check Contract

The selection method accepts five inputs:

1. the exact completion claim;
2. the changed or diagnosed seams and their stable observables;
3. checks required by the user, repository, or focused workflow;
4. current evidence classified as fresh direct, fresh partial, stale,
   indirect, or missing; and
5. risk, reversibility, and the cost or availability of candidate checks.

It produces one validation decision containing:

- proof obligations for every affected claim and contract;
- mandatory checks, which are never optimized away;
- the smallest selected set that covers the remaining obligations;
- why a smaller set is insufficient;
- why a broader set is unnecessary, or the exact reason it is required;
- skipped, blocked, stale, or indirect evidence and residual risk; and
- one verdict: verified ready, conditionally ready, or not yet verified.

Selection follows this order:

1. Resolve explicit user, repository, and focused-workflow requirements.
2. State the claim and affected seams before naming commands.
3. Map each seam to a stable observable and a proof obligation.
4. Reuse only fresh evidence that actually covers that obligation.
5. Choose the cheapest repository-owned check set that covers all uncovered
   obligations.
6. Broaden only when a required rule says so, the changed seam controls broader
   execution, consumers cannot be covered narrowly, or the narrower evidence is
   unavailable or unreliable. Record the reason.
7. If a check fails, diagnose that failure first. Add a check only when the
   diagnosis reveals another affected seam or obligation; failure alone is not
   permission to run the complete gate or expand the change.
8. Re-read the primary completion criterion and report only the evidence
   actually obtained.

The complete canonical gate is selected when at least one of these conditions
is true:

- a more specific rule explicitly requires it for this change;
- the gate selector, test harness, build or packaging graph, dependency or
  lockfile authority, generator, installer, release path, or canonical gate
  itself changed;
- the change crosses shared or public compatibility seams that cannot be
  covered by a bounded set of consumer or contract checks; or
- no smaller reliable check exists and the complete gate is the least broad
  available evidence, with that gap stated explicitly.

The following are not sufficient reasons: the repository has a complete gate;
the edited file is Markdown; the task will be committed or opened as a pull
request; a focused check failed; a mixed task also contains documentation; or
the complete gate is familiar and easy to invoke.

## Evaluation Contract

### Fixture And Oracle Design

Add `evaluations/progressive-validation-selection/` with `cases/`, `fixtures/`,
`rubric.yaml`, `README.md`, and a result schema. Freeze cases and deterministic
oracles before the runtime instruction changes.

Generalize `scripts/run_writable_agent_eval.py` so a case resolves its fixture
from the case file's evaluation root instead of the current hard-coded
`ai-native-implementation` root. Parse the Codex JSONL tool-call stream captured
by the runner outside the writable fixture workspace, normalize shell command
forms into case-declared check families, and retain the raw command plus its
normalized classification in `result.json`. The executor cannot write or edit
this post-run capture.

Repository-owned check wrappers may emit structured begin/end records for
diagnostics, but executor-controlled stdout is never execution truth. Run the
executor behind a mandatory Linux `bwrap` boundary with a minimal root: the
prepared workspace is writable only at the case's pre-existing declared change
targets, while `.git` and every other original fixture file are read-only; the
source repository, evaluation cases, rubric, and user home are absent. Do not
fall back to an unconfined executor when that boundary or its preflight cannot
be established.

The trusted Codex process may read its isolated authentication file and reach
the model service, but model-generated commands must use a fixed named
permission profile that denies `/output` reads and disables network access.
Do not add an independent generic-shell network namespace: the named profile
is the version-frozen, real-machine-validated network control for model
commands. Exercise a direct non-shell executable through the same Codex
permission profile with a synthetic credential marker and loopback listener.
This control must fail closed without reading or printing real authentication
material.

Place runner-owned PATH shims and a per-run dual-FIFO transport in a
runner-private runtime read-only bind. The executor receives write-only access
to the request FIFO and read-only access to the response FIFO. A request is one
writer's record no larger than `PIPE_BUF`; a response carries
`protocol_version` and `request_id` and is bounded by size and timeout limits.
An advisory transaction lock serializes cooperating shim request/response
pairs. Because the response FIFO must be readable by the executor shim under
the same UID, a malicious executor can steal a response and cause a request-ID
mismatch or timeout; classify that fail closed as harness-invalid/DoS. Response
writes remain denied by mode `0400` and the read-only bind. For every accepted
response, the runner generates a random 64-hex receipt; after fully validating
the response, the shim emits that receipt. The oracle matches the runner-memory
receipt to each actual alias in order and never places a token in the public
result. A stolen response thus lacks a receipt and is harness-invalid even when
its error code collides with a legitimate nonzero exit. The broker must ignore
caller-supplied family, identity, working directory, and result fields.
It maps only an exact case-declared canonical argv, fixes the case and workspace
itself, executes at most that one command inside a fresh networkless check
`bwrap`, and records its real per-invocation exit in runner memory. An executor
can bypass the advisory lock and directly write an exact canonical request,
which can execute that real fixed check and create a runner event. It cannot
forge a valid reconciled result or event: reconcile every runner-memory broker
event one-to-one and in order with the raw command plan captured outside the
executor, and invalidate missing, extra, reordered, bypassed, ambiguous, or
unmatched raw/event evidence. A direct or unwrapped full-gate command remains
conservatively forbidden even when it bypasses the broker. Preserve shell
compound operators, use only broker exits to decide `&&` and `||` branches, and
never copy the aggregate parent-shell exit or wrapper stdout to child
invocations. Post-run verification commands use a separate runner phase and are
excluded by phase identity.

Case YAML declares required and forbidden command families, required exit
states, and any ordered sequence such as P09's focused failure, diagnosis, and
focused pass. S1 freezes normalization rules for direct paths, shell compound
commands, package-manager aliases, and repository wrapper entrypoints. Negative
controls must include forged wrapper stdout, a FIFO request with caller-forged
fields, an unwrapped or shim-bypassing complete-gate invocation, a compound
command containing an executed forbidden check, and missing, extra, or
reordered raw/broker evidence.

The reconciled runner capture plus broker record is the deterministic
command-selection oracle. A
blind judge assesses diagnosis, relevance, unsupported claims, and residual-risk
reporting. Neither replaces the other, and a judge cannot overturn a
deterministic critical failure. Executor prompts must exclude expected event
labels, rubric text, target outcomes, and arm identities. Blind packets must
exclude source names, commit roles, arm mapping, and intended preference. Hash
the case set, prompts, source refs, raw captures, normalized observations,
scorecard, and arm map. Any leakage, ambiguity, or hash mismatch invalidates the
run and is recorded rather than overwritten.

### Blind Scoring Interface

Freeze `judge-prompt.md`, `rubric.yaml`, and the score schema in S1. Use two
fresh judge tasks with the same fixed judge model and reasoning effort, no
executor turns, and independently randomized A/B labels. Each case receives
integer scores from 0 to 2 for obligation reasoning, check relevance, failure
diagnosis, evidence honesty, and user burden; a preference of A, B, or tie; a
short evidence-based reason; and zero or more predefined critical-failure codes.

The score schema defines every anchor, including when a dimension is not
applicable. Judges see the user prompt, final diff, normalized command and
result chronology with neutral command names, and final answer. They do not see
the target list, source identity, expected event set, aggregate metrics, or
other judge's output.

Deterministic required/forbidden observations decide proof coverage and command
selection. Judges decide only qualitative diagnosis and claim quality. If the
judges disagree, retain both results; do not average a preference into a false
consensus. A qualitative regression blocks rollout only when both judges prefer
the baseline on the same case and identify the same critical dimension. A tie
or one-judge disagreement is reported and bounded by the deterministic rule.

### Controls And Runs

The baseline is the exact commit after the evaluation harness and inert vendor
tree are frozen but before activation, template, or calibration-routing changes.
The candidate is the exact activation commit. This compares the accepted bundle;
it does not establish that any one upstream source caused the result.

Use the same model, reasoning effort, tools, permissions, prompt, case tree, and
turn budget for both arms. Use a fresh workspace and isolated `CODEX_HOME` for
every run. Counterbalance arm order. Run every primary and holdout case once per
arm as smoke. Continue only when the harness is valid, both arms preserve
authority and workspace safety, and both arms cover mandatory proof obligations.
When eligible, continue every primary and holdout case until each arm has three
valid runs. Baseline over-validation remains eligible for comparison; a
candidate critical failure does not. If cost, capacity, or another boundary
prevents the full repeat set, the result may authorize only a specifically
bounded canary and cannot authorize repository-wide rollout.

Store raw trajectories and isolated homes outside the repository. Commit only
the frozen public inputs, hashes, per-run observations, aggregate scores,
contamination log, and bounded conclusion.

### Metrics And Decision Rule

Critical metrics are:

- proof-obligation coverage: 100%;
- explicit local mandate adherence: 100%;
- unsupported completion claims: 0;
- authority or workspace-safety violations: 0;
- unnecessary complete-gate use on P01 and eligible holdouts: 0; and
- failure-only mechanical widening on P09: 0.

An unnecessary check is one that covers no uncovered proof obligation, is not
required by a more specific rule, and is not justified by a newly observed
seam. Record it by check event, not by wall time alone. Time, token use, command
count, and complete-gate count are secondary metrics considered only after all
critical metrics pass.

Reject activation on any candidate critical failure. Hold at a bounded canary,
with no improvement claim, if critical metrics pass but the candidate shows no
strict reduction in unnecessary expansion on a predeclared target case.
Proceed to downstream rollout only when the candidate passes every critical
metric, shows that strict targeted improvement, has no deterministic selection
regression, and has no case where both blind judges prefer the baseline on a
critical dimension. A single qualitative disagreement is recorded, not treated
as an automatic veto. Record mixed or inconclusive evidence honestly; do not
reinterpret it as acceptance.

## Compatibility, Risks, And Rollback

The principal compatibility risk is instruction precedence: stale local rules
continue to require full gates until migrated. That is safe over-validation,
not a reason to let the global skill override repository authority.

Installing a third-party protocol in AO-worker changes the profile's current
public first-party-only contract. Treat that as an explicit compatibility change
owned by S4: update the root README and installer assertions in the same review
unit, prove the shared list contains exactly one pinned skill, and reject the
slice if AO-worker cannot preserve its isolated-home and owned-link guarantees.

Other risks are implicit-trigger expansion, overlapping calibration and coding-
protocol ownership, hidden under-validation, evaluation leakage, upstream drift,
and third-party license mistakes. Exact allowlisting, Exit and composition
tests, obligation coverage, frozen blind packets, immutable refs, copied
applicable license material, and provenance review address those risks.

Rollback is layered and reversible:

1. disable the exact implicit-invocation exception;
2. move `coding-protocol` from the shared managed array to an explicit retired-
   shared-third-party cleanup array while its source path remains available;
3. run the installer against every standard and AO-worker home recorded in the
   private installation registry, move each record through cleanup-pending, and
   verify that owned links to this repository are gone while foreign files or
   links with the same name are preserved;
4. only after that readback, remove the managed category entry and restore the
   prior root README, global template, and calibration trigger;
5. retain the vendored source as inert provenance or remove it in a later
   reviewed cleanup; and
6. revert each downstream repository independently without changing siblings.

Unknown or unavailable installation homes remain explicitly unresolved;
removing an installer array entry is not evidence that an already installed
link was removed. Installer tests must cover standard and AO-worker owned-link
cleanup, foreign-link preservation, idempotent rerun, and source-tree retention
through the cleanup phase. Rollback is complete only when every registered
record is removed and no unresolved home is being claimed as covered.

Do not roll back by weakening required checks, deleting evaluation failures, or
changing the complete CI gate. If an external installation outcome is unknown,
read it back before retrying installer changes.

## Review And Delivery Splits

Use independent review units:

1. provenance plus frozen evaluation harness and oracle;
2. inert source import plus validation-selection reference;
3. installer, implicit exception, global fallback, and calibration routing;

Keep one writer per unit and preserve unrelated work. Review must distinguish
static wiring, deterministic selection evidence, blind qualitative judgment,
