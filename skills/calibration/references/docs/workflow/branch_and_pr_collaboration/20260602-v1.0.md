# Branch and PR Collaboration Sources

For GitHub-hosted repositories, use GitHub flow as the default collaboration
workflow, subject to the repository's own contribution and release contracts.
Read the relevant official source when a decision depends on platform behavior:

- [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow):
  branch-based collaboration, review, merge, and branch cleanup.
- [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches):
  protection settings, required checks, reviews, and bypass behavior.
- [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue):
  queue suitability, configuration, and validation against the target branch.

Verify the repository's actual rulesets, branch protection, and merge settings;
this reference does not establish that protection is enabled. Repository-owned
rules define release branches, multi-version maintenance, and special staging
or deployment workflows. For other hosting platforms, use their official
workflow documentation and the repository's local contract.

Platform documentation and tool availability do not grant operation authority.
Use the existing [ownership and delivery boundaries](../../../discipline/harness.md#repository-delivery-feedback-loop)
and [verification requirements](../../../discipline/verification.md).

This path is retained for existing links; it now routes to upstream guidance
instead of maintaining a parallel branch workflow specification.
