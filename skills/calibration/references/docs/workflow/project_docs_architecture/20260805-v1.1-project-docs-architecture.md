# Project Docs Architecture

Version: v1.1
Date: 2026-08-05
Status: current
Supersedes: [20260527-v1.0-project-docs-architecture.md](20260527-v1.0-project-docs-architecture.md)

This document defines the default cross-project structure for durable project
documentation. Repository-local documentation may be stricter. When a local
repository already has a different established path, preserve it until a
reviewed migration changes its authority map, links, and validation.

## Purpose

Project `docs/` stores long-lived knowledge that contributors and agents need to
reuse:

- current architecture, domain boundaries, and active contracts;
- settled decisions and their consequences;
- implementation and migration plans;
- durable testing, benchmark, tutorial, operational, and compatibility
  guidance; and
- reviewed supporting assets and traceable historical material.

Raw command output, temporary transcripts, and unprocessed task observations do
not belong in `docs/`. Task-level judgment and expectation-versus-actual
records belong in `.traces/` until a stable rule or contract is promoted.

## Preferred Greenfield Layout

Use the smallest structure that fits the project. Do not create empty
directories merely to match this list.

```text
docs/
  README.md
  architecture/
  decisions/
  implementation-plans/
  testing/
  benchmarks/
  tutorials/
  how-to-guides/
  runbooks/
  compatibility/
  assets/
  archive/
```

`docs/README.md` is required whenever `docs/` exists. Every other directory is
created only when its content trigger exists.

## Directory Roles And Creation Triggers

| Directory | Role | Create when | Authority or lifecycle |
| --- | --- | --- | --- |
| `README.md` | Entry point, reading order, current authority map, and active plans | `docs/` exists | Current navigation authority; not a replacement for source documents |
| `architecture/` | Current system facts, ownership boundaries, data flow, and active contracts | The project has durable current structure or contract knowledge | Current authority; do not use for unapproved future direction |
| `decisions/` | Settled consequential choices, alternatives, rationale, consequences, and reopening conditions | A decision has material alternatives or durable consequences | Current decision authority; superseded records remain traceable |
| `implementation-plans/` | Decision-complete execution slices, dependencies, risks, verification, and acceptance | An accepted change needs coordinated or staged implementation | Active execution guidance; completed plans become historical evidence |
| `testing/` | Durable test strategy, quality gates, smoke checks, real-data validation, and acceptance criteria | Validation rules need reuse beyond one task | Current validation authority for the documented scope |
| `benchmarks/` | Reproducible measurement protocols, environments, baselines, output checks, and results | A performance, numerical, or scale claim needs repeatable evidence | Benchmark evidence; do not use for unsupported headline numbers |
| `tutorials/` | Guided learning paths that help a reader acquire a new capability | The project maintains a reusable beginning-to-capability learning path | Team-owned durable teaching material |
| `how-to-guides/` | Task-oriented instructions for one known outcome | A competent reader needs repeatable steps for a concrete task | Team-owned operational or development guidance |
| `runbooks/` | Controlled operational procedures with prerequisites, verification, recovery, rollback, and escalation | A procedure is production-adjacent, high-risk, or tightly controlled | Current operational authority for the documented procedure |
| `compatibility/` | Verified constraints, deviations, failure signatures, and safe adaptations at external or third-party boundaries | Repeated evidence establishes a reusable external-behavior rule | Current compatibility authority; raw exploration remains in `.traces/` |
| `assets/` | Repository-owned images, diagrams, and editable sources referenced by docs | A durable document needs a versioned supporting asset | Supporting material only; it is not a document type |
| `archive/` | Superseded or historical material retained for traceability | A replaced document has continuing reference value | Lifecycle state, not a document type; archived material is not current authority |

The preferred shared names are `tutorials/` and `how-to-guides/`, following the
learning-oriented distinction in [Diataxis tutorials](https://diataxis.fr/tutorials/)
and [Diataxis how-to guides](https://diataxis.fr/how-to-guides/). `learning/`
and `cookbook/` are not default names for new cross-project guidance, although
a repository may retain an established local convention until migration.

`field-manual/` is not a default shared directory. If a repository already uses
it for external or third-party black-box exploration, keep that repository-local
convention while the material is being classified. For new durable rules, use
`compatibility/` when the primary authority is verified external behavior.

## Document Selection Boundaries

Select one primary document type before writing. Use the document-type router
for the minimum contract, and use the directory role for placement:

```text
guided capability acquisition       -> tutorial in tutorials/
one concrete ordinary task          -> how-to guide in how-to-guides/
controlled or high-risk operation   -> runbook in runbooks/
opaque external compatibility rule -> compatibility record in compatibility/
current system truth                -> architecture overview in architecture/
settled consequential choice        -> decision record in decisions/
decision-complete execution path   -> implementation plan in implementation-plans/
reproducible measurement claim      -> benchmark record in benchmarks/
durable validation contract        -> test plan in testing/
```

Interactive teaching is a process, not automatically a project document. A
`teach` interaction may remain ephemeral. Only an explicit request to preserve
the result creates a team-owned document, which is then routed by the table
above. Personal learning missions, preferences, and mastery records are not
project authority.

## External Method And Local Authority

Use established external methods for general authoring guidance, but keep the
local contract thin and explicit. Useful references include:

- [Diataxis](https://diataxis.fr/) for tutorial and how-to distinctions;
- [Architectural Decision Records](https://adr.github.io/) and
  [MADR templates](https://adr.github.io/adr-templates/) for decision records;
- [AWS runbook guidance](https://docs.aws.amazon.com/wellarchitected/2023-10-03/framework/ops_ready_to_support_use_runbooks.html)
  for operational readiness; and
- compatibility-policy examples such as the
  [Kubernetes version skew policy](https://kubernetes.io/releases/version-skew-policy/)
  and [MDN compatibility tables](https://developer.mozilla.org/en-US/docs/MDN/Writing_guidelines/Page_structures/Compatibility_tables).

External pages provide method, not silently changing project policy. The local
contract defines the selected type, adopted invariants, repository requirements,
precedence, and completion evidence. Repository-local documentation owns
project facts, commands, versions, and executable validation.

Do not copy large external guides into the repository. Keep enough local
selection and acceptance guidance to remain usable if an external link is
temporarily unavailable.

## README Requirements

`docs/README.md` should tell a new contributor or agent:

- what to read first;
- which architecture document is current;
- where the active implementation plan lives;
- where testing and validation standards live; and
- which documents are historical or superseded.

The README is navigation, not a second copy of the source documents.

## Relationship To Repository Instructions

The canonical `AGENTS.md` content boundary is defined by the
[repository harness](../../../discipline/harness.md). Project `docs/` remain
the durable project authority, with `docs/README.md` as the navigation
entrypoint. Do not copy operational instructions into architecture documents
when the harness already owns them.

## File Naming

For new dated documents, use lowercase kebab-case:

```text
YYYYMMDD-vMAJOR.MINOR-topic-kind.md
```

Recommended `kind` values include `architecture`, `contract`, `test-plan`,
`benchmark`, `implementation-plan`, `migration-plan`, `decision-record`, and
`closeout`. Avoid spaces, colons, mixed case, and temporary names. Keep
`README.md` as the undated navigation exception.

Existing documents do not need a bulk rename. Apply the rule to new documents,
and migrate old names only during a separately reviewed natural edit.

## Lifecycle And Promotion

Current documents are the default authority. When a document is replaced, mark
the old document as superseded and link to its replacement. Move it under the
repository's archive convention only when retaining it adds traceability value.
An archived document keeps its original document type and is not a current
source of truth unless a current document explicitly cites it.

Use `.traces/` for raw trial-and-error, task-level retrospectives, and short-lived
observations. Promote a trace into `docs/` only after it becomes a stable rule,
contract, test standard, decision, reusable procedure, or verified external
compatibility fact.

## Precedence

Resolve conflicts in this order:

1. explicit user or project-owner requirements;
2. repository-local documentation and executable validation;
3. this shared project-docs architecture and document-type router; and
4. external methodology references.

An external method change does not change local policy until it is explicitly
reviewed and adopted. During a migration, `docs/README.md` and the repository's
authority map identify the current path; do not infer authority from a directory
name alone.

## Minimal Authoring Contract

Use the smallest local contract that makes selection and acceptance clear. A
document-type file should normally contain:

```text
Use When
Method Reference
Local Requirements
Complete When
```

`Do Not Include` is not required. Put common selection boundaries in the
document-type router. Keep a short negative boundary only when omitting it
would create a material authority, risk, lifecycle, or repeated-classification
failure.
