# Acme Parser 4.2 Empty-Tag Compatibility

Date: 2026-08-13

Status: current

## Boundary and scope

This record applies to XML input consumed by Acme Parser 4.2 when downstream
code must distinguish an empty string from a missing field. The original
verification did not capture the operating system or parser configuration, so
do not generalize the result to other versions or environments without a
fresh fixture run.

## Expected contract

An explicitly empty value must remain present as an empty string after parsing.
An intentionally absent value may remain a missing field.

## Verified behavior

On 2026-08-12, three fixtures (A, B, and C) produced the same result with Acme
Parser 4.2:

| XML input | Parsed result |
| --- | --- |
| `<tag/>` | field is missing |
| `<tag></tag>` | field is present as an empty string |

This is an observed parser compatibility constraint. It is not a claim about
XML semantics in general or about other Acme Parser versions.

## Failure signature

A caller serializes an intended empty string as `<tag/>`, but the parsed object
omits the field. Downstream code then handles the value as missing rather than
empty.

## Safe adaptation

At XML-producing boundaries that feed Acme Parser 4.2:

- emit `<tag></tag>` when the field must be preserved as an empty string;
- reserve omission for values that are intentionally missing; and
- add a paired regression fixture covering both encodings when the distinction
  matters to a caller or artifact.

Do not rewrite intentionally absent fields into explicit empty elements.

## Reproduction and review

To recheck the constraint, parse two otherwise identical documents with Acme
Parser 4.2, varying only `<tag/>` versus `<tag></tag>`, and assert the two
results shown above.

The maintainers of the Acme Parser integration own follow-up. Re-run the paired
fixture and review this record when the parser version, parser configuration,
or XML serializer changes. Replace or supersede this record if representative
fixtures demonstrate different behavior.
