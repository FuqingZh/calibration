# Acme Parser 4.2 Empty-Tag Compatibility

- Record version: v1.0
- Date: 2026-08-13
- Status: current
- External boundary: Acme Parser 4.2

## Compatibility contract

When an intentionally empty `tag` must remain present as an empty string in
Acme Parser 4.2 output, provide an explicit start and end tag:

```xml
<tag></tag>
```

Do not use `<tag/>` for that contract, because version 4.2 treats that form as
a missing field.

## Verified behavior

| Input form | Observed output |
| --- | --- |
| `<tag/>` | The field is missing. |
| `<tag></tag>` | The field is present with an empty-string value. |

Both outcomes were reproduced in fixtures A, B, and C on 2026-08-12. The
reusable evidence identifies the parser version and fixture set; it does not
retain an operating-system, runtime, or parser-configuration matrix. No claim
is made for other Acme Parser versions or configurations.

## Failure signature

A producer intends to send an empty string using `<tag/>`, but the parsed
result has no field. This is the known version-4.2 compatibility behavior, not
evidence by itself that the downstream field-mapping code removed the value.

## Safe adaptation

- Emit `<tag></tag>` wherever the distinction between an empty string and a
  missing field matters.
- Keep a parser-boundary test that asserts the field is present and equals the
  empty string.
- Limit the workaround to the Acme Parser 4.2 boundary; do not normalize every
  self-closing element without a caller contract requiring it.

Affected callers are input producers, fixtures, and boundary tests that target
Acme Parser 4.2 and rely on missing and empty values being distinct.

## Reproduction

1. Parse otherwise equivalent inputs containing `<tag/>` and `<tag></tag>`
   with Acme Parser 4.2 under the target integration configuration.
2. Inspect both field presence and field value in the parser output.
3. Confirm that the self-closing form omits the field and the explicit form
   produces a present field whose value is the empty string.

## Review conditions

Revalidate this record when the parser version or configuration changes, or
when a target environment produces a different result. The maintainer making
that boundary change owns the revalidation and should update or supersede this
record with the new fixture evidence.
